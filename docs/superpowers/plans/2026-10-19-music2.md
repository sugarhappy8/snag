# Music 2.0 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give the Musician the layers Business has (a label deal with a recoupment ledger, format eras, a seeded chart against named rival acts, a touring P&L, seven events, honest hints, a master buy-back an heir can inherit) on the shared career kit, lifting the audit rubric from 2 to 4.

**Architecture:** A pure move of the profile and job code out of `music.ts` into `music-job.ts` comes first, so no new module ever imports `music.ts`. `music-data.ts` holds the tables, `music-state.ts` an owner-stamped record at `special.music.sim` (`defineCareerState`, migrated from the legacy profile without touching it), `music-market.ts` the format mix, the waterfall, the chart and `bookRelease`, `music-label.ts` the negotiation and the deal year, `music-tour.ts` the tour P&L, `music-events.ts` six crises plus the dispute, `music-menu.ts` the read-only menus. `music-sim.ts` is one `settleYear` entry registered in `kit/careers.ts`; the legacy `yearlyMusic` keeps its behaviour for a life with no record and skips only the deal year and the awards once the sim owns the life.

**Tech Stack:** TypeScript (strict), Vitest (`npx vitest run --maxWorkers=1 <files>`), no new dependencies, no `src/ui` change.

**Spec:** `docs/superpowers/specs/2026-10-19-music2-design.md` ("S4.3" = its section 4.3; it wins over the digests). Kit and conventions: `docs/superpowers/specs/2026-10-19-careers-slice1-design.md`, `docs/superpowers/plans/2026-10-19-careers-slice1.md` and `src/game/special/kit/*`. **Plan decisions** (where the spec is silent or reads two ways; the tasks use these names and values):
- The sim hook (Task 4) comes before the label (Task 5), so each guard in `yearlyMusic` lands with the code that replaces the line it skips: the deal-year guard with `stepDeal` (Task 5), the awards guard with the sim's awards (Task 7). This order never leaves an adopted life unpaid between two commits (S9 now carries the same order). Menus are wired in Task 8, so Tasks 5 to 7 are reached through scripts, `music.tour` and tests.
- The digest gave a sample claim p = 0.40 for "a top-20 peak" and 0.15 for "a lower one", but no row charts below 20 (`chartLen` is at most 20). One function `claimOdds(kind, peak)` in `music-data.ts` reads it as: sample peak 1 to 10 is 0.40, 11 to 20 is 0.15; plagiarism peak 1 to 10 is 0.04; anything else 0 (S4.7 and S4.8 say the same). The Release Plan hint says "if it charts top 10".
- A legacy deal's `royalty` is exactly 1 (the normalizer allows it only while `legacy` is true; the waterfall never reads it). A renewal royalty is `baseRoyalty(tier)` plus 0.02, so a grandfathered life is never worse than a fresh one.
- `field` 0 (before 1900) gives `peak` 0 whatever the rank. `LedgerRow.lastLabel` is the label's take in the last settled year (kept plus recouped). `fill` mods multiply the clamped fill, capped at 1.
- `planEffect` lives in `music-market.ts` (`bookRelease` reads it); the Release Plan script and row live in `music-label.ts`. `signDeal` returns `{ job, quit, fromBand }`, writes no text, and applies its `data` argument (a `Partial<MusicJob>`) last.
- A failed push on a renewal withdraws it: the deal ends as `dropped` and the label lets you go (`leave(g, 'fired')`).
- "Last year's release" (the `award` gate) is the latest `viewMusic(g).discography` entry with `age === g.character.age - 1`, the same read the legacy awards block used, so legacy-tail and ledger releases both count. A sample claim is drawn first, then a plagiarism claim, each from its own seeded key.
- `chartLen` is `min(20, max(5, round(field / 2)))`: a roster can run a few over 40, and a row never charts below 20. The draft type in `music-market.ts` is `BookDraft`, because `music.ts` already has a local `ReleaseDraft`. `DealOffer` and `DisputeData` are `type` aliases, not interfaces: an interface is not assignable to the kit's `Record<string, Json>` modal data.
- A deal lifted from a legacy job has id `'legacy'`, and its renewal gets a fresh `nextId(s, 'd')`. A label id is always `labelId(name)` (S3 table in Task 1), for the roster, the floor label and a lifted deal alike.
- A refused tour (cash short, a gate closed) claims nothing and spends nothing: the resolver pre-checks owner, year and replay without marking `s.done`, checks the gates and the cash preflight, and only then calls `claimChoice`, so the player can pick again.
- S9 and S7 are updated to this order, to the `LEGACY` set below and to the two extra test files (`music-sim`, `music-lifetime`).
